# 認証機能仕様書

## 概要
BRANU営業支援システムの認証機能。AWS CognitoとGoogle OAuth 2.0を使用したシングルサインオン（SSO）とNext.jsサーバーサイドセッション管理を提供。

## 認証フロー

### 1. Google OAuth 2.0認証

#### Next.js担当: フロントエンド処理
1. ユーザーが「Googleでログイン」ボタンをクリック
2. `GET /api/auth/google`にリクエスト送信
3. レスポンスのredirectUrlへリダイレクト
4. 認証完了後、コールバック処理で認証結果を受け取り
5. 成功時は事例検索画面（トップ画面）へリダイレクト

#### Next.js担当: 認証データ処理
- 認証成功時にユーザー情報をRDSに保存・更新
- ユーザー権限・ドメインチェック処理実行

#### FastAPI担当: セッション管理
- AWS Cognito経由でGoogle認証URLを生成
- 認証成功時にセッション生成・保存（Redis）

### 2. ドメイン制限
- **許可ドメイン**: @branu.jp
- **拒否時エラーメッセージ**: "このアカウントではログインできません"
- 許可されていないドメインでのログイン試行を防止

## セッション管理

### 1. ログイン状態保持オプション
- **チェックボックス**: "ログイン状態を保持する"
- **デフォルト状態**: チェックなし

### 2. セッション保存方式

#### Next.js担当: Cookie管理
- **Cookie送信**: API呼び出し時にHttpOnly Cookieを自動送信
- **セッション検証**: `/api/auth/session`でログイン状態確認
- **ログアウト**: `/api/auth/logout`でセッション終了

#### FastAPI担当: セッション管理
**チェックボックスON時（長期認証）**
- **保存場所**: Redis + HttpOnly Cookie
- **持続期間**: 長期間（30日間、Redis TTL設定）
- **Cookie設定**: Persistent Cookie（有効期限30日）

**チェックボックスOFF時（セッション認証）**
- **保存場所**: Redis + HttpOnly Cookie
- **持続期間**: ブラウザセッション中のみ（Redis TTL設定）
- **Cookie設定**: Session Cookie（ブラウザを閉じると削除）

### 3. スケール対応

#### コンテナスケーリング時の考慮事項
- **Redis活用**: 複数インスタンス間でのセッション共有にRedisを使用
- **ステートレス設計**: アプリケーションサーバーはステートレス、セッション状態はRedisで管理
- **負荷分散対応**: どのインスタンスにアクセスしても同一セッション状態を維持

#### セッション管理フロー
```
ユーザー認証 → AWS Cognito → Next.jsセッション → Redis保存 → HttpOnly Cookie
```

## 状態管理

### 1. ログイン状態検証

#### Next.js担当: 状態管理
- **ページ読み込み時**: `/api/auth/session`でセッション有効性チェック
- **API呼び出し時**: HttpOnly Cookieによる自動認証
- **定期チェック**: バックグラウンドでの状態確認

#### Next.js担当: ユーザー情報取得
- **ユーザー確認**: 認証されたユーザーの詳細情報をRDSから取得
- **権限チェック**: ユーザーの権限・ステータス確認

#### FastAPI担当: セッション検証
- **Cookie検証**: リクエストのHttpOnly Cookieからセッション情報を取得
- **Redis確認**: セッションの有効性をRedisで検証
- **レスポンス**: 認証状態情報を返却

### 2. ログアウト処理

#### Next.js担当: ログアウト操作
- **手動ログアウト**: ユーザー操作で`/api/auth/logout`を呼び出し
- **自動ログアウト**: セッション期限切れ時の自動処理
- **画面遷移**: ログアウト後はログイン画面へリダイレクト

#### FastAPI担当: セッション削除
- **Redis削除**: セッション情報をRedisから削除
- **Cookie削除**: HttpOnly Cookieを無効化

### 3. ログアウト機能の位置づけ

#### 利用頻度と必要性
- **手動ログアウトの必要性**: 限定的（共用PC利用時、セキュリティ意識の高いユーザー等）
- **主な認証終了方法**: 自動期限切れ（短期: ブラウザ閉じると削除、長期: 30日で期限切れ）
- **API提供理由**: セキュリティのベストプラクティスとして実装
- **UI設計方針**: 簡素化（目立たない場所に配置、強制的な利用は促さない）
- **想定利用頻度**: 低頻度（大部分のユーザーは自動期限切れに依存）
